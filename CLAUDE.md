# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

Workspace for the **Pokémon TCG AI Battle Challenge** on Kaggle — building an AI agent that plays the Pokémon Trading Card Game. Two linked competitions:

- **Simulation category** (https://www.kaggle.com/competitions/pokemon-tcg-ai-battle) — submit an agent bundle; agents play ladder matches (Gaussian rating). Up to 5 submissions/day; only the **two most recent** submissions count. Entry deadline 2026-08-09, final submissions 2026-08-16. No prize itself but prerequisite for Strategy.
- **Strategy category** (this repo's namesake, `pokemon-tcg-ai-battle-challenge-strategy`) — a ≤2,000-word written report on the approach. Judged: model methodology 70%, deck strategy 20%, documentation 10%. Entry deadline 2026-09-06, submissions 2026-09-13. Top 8 teams win $30,000 each; ladder rank helps but does not decide.

Match format: 60-card decks from the organizer-provided card pool, max **10 minutes per match — timeout = automatic loss**. The engine presents only legal moves, so the agent's entire job is choosing among given options.

`pokemon-tcg-ai-battle/` contains the downloaded competition materials. **License: competition use only** — do not republish or share the engine/card data; it must be deleted when the competition ends. Treat that directory as read-only reference; build our agent code outside it.

## Layout

- `pokemon-tcg-ai-battle/sample_submission/sample_submission/` — the agent template and the **local simulator SDK**:
  - `main.py` — agent entry point (the file Kaggle calls)
  - `deck.csv` — 60 lines, one card ID per line (deck must be legal: 60 cards, ≤4 copies per name, ≤1 ACE SPEC, etc.)
  - `cg/` — Python package wrapping the prebuilt native engine via ctypes (`cg.dll` on Windows, `.so`/`.dylib` elsewhere; auto-selected in `cg/sim.py`)
- `pokemon-tcg-ai-battle/ptcg_engine/ptcgProgram 22/` — C++20 header-only source of the same engine ("cabt Engine"), VS2022 `game.sln`. Reference only; rebuilding it is never required for agent work.
- `pokemon-tcg-ai-battle/EN_Card_Data.csv` / `JP_Card_Data.csv` — the card pool (ID, name, stage, HP, type, attacks, effect text). The two `Card_ID List_*.pdf` files are 130–180 MB image scans — never read them; use the CSVs.

## Agent contract (`main.py`)

```python
def agent(obs_dict: dict) -> list[int]
```

- **First call**: `obs.select is None` → return the deck as a list of 60 card IDs.
- **Every other call**: return option **indices** into `obs.select.option`, with `minCount <= len(result) <= maxCount`, each index `0 <= i < len(obs.select.option)`, no duplicates. `minCount` can be 0.
- `deck.csv` is read from cwd locally but `/kaggle_simulations/agent/deck.csv` on Kaggle — keep the sample's fallback path logic.

## The `cg` API (import from the sample_submission dir)

- `cg.api` — `Observation` dataclass tree (`State` → 2×`PlayerState` → `Pokemon`/`Card`), all enums (`SelectType`, `SelectContext`, `OptionType`, `LogType`, `AreaType`, ...), plus `all_card_data()` / `all_attack()` for the full card/attack database from the engine. `to_observation_class(obs_dict)` converts the raw dict. **The organizers may append new enum members and dataclass attributes mid-competition** — write code that tolerates unknown values.
- `cg.game` — local battle loop: `battle_start(deck0, deck1)` → repeatedly `battle_select(indices)` → `battle_finish()`. `state.result` / `LogType.RESULT` signals the winner. `visualize_data()` dumps visualizer JSON.
- **`cg.utils.to_dataclass` leaves leaf-enum fields as raw ints, not enum instances.** It only recurses into nested dataclasses; a scalar or list-of-int field annotated as an enum type (e.g. `Card.energyType`, `Attack.energies` elements) comes back as a plain `int`. `==` against the enum still works (Python `IntEnum` compares equal to `int`), but `.name` raises `AttributeError` on the raw int. Wrap with the enum constructor (`EnergyType(x)`, `CardType(x)`) at the point of use whenever `.name` or other enum-only behavior is needed. Found in `src/ptcg/factory/deck_quality.py` (2026-08-10).
- **`all_card_data()` / `all_attack()` share a native buffer in the engine DLL and are NOT thread-safe.** Concurrent first calls from multiple threads (e.g. two request-handler threads racing a cold `lru_cache` in a threaded HTTP server) produce torn/corrupted JSON — observed as `JSONDecodeError` plus inconsistent card counts across threads. Any multi-threaded Python consumer of these two calls must serialize access with a lock around the DLL call (not just around the cache-dict lookup — an `lru_cache`-decorated builder function still races on a cold miss) and/or warm the cache single-threaded before accepting concurrent traffic. Reference implementation: `deck_quality._DLL_LOCK` + `_card_db()`/`_attack_db()` in `src/ptcg/factory/deck_quality.py`, with `run_server` warming both caches before `serve_forever()`.
- **Search API** (`cg.api.search_begin` / `search_step` / `search_end` / `search_release`) — the planning forward-model. `search_begin` takes the agent's own `Observation` **plus predictions of all hidden zones** (your prize order, opponent's deck/prizes/hand, face-down active) and returns a `SearchState` you can step through selections like a game tree (`manual_coin=True` lets you branch on coin flips). This determinization interface is the intended basis for MCTS/lookahead agents. Call `search_release`/`search_end` to reclaim memory — searches leak otherwise.
- Hidden info in `Observation`: opponent `hand` is `None` (only `handCount`), face-down prizes/active are `None`, own deck is count-only (`deckCount`) except during deck-selection contexts (`select.deck`).

## Things that matter when building the agent

- **Time budget is per-match (10 min total), not per-move.** Any search must be time-boxed; a timeout is a loss, so favor an anytime algorithm with a hard deadline per decision.
- Deck IDs reference `EN_Card_Data.csv`; the sample deck (`deck.csv`) is mostly filler (35× card ID 3 = Basic Water Energy — verified via `grep -c "^3$" deck.csv`, not 34× as a stale earlier count claimed) — deck construction is a real, scored part of the strategy (20% of Strategy judging).
- `Observation.logs` carries everything that happened since the last decision (draws, coin flips, KOs, opponent's visible plays) — it is the only way to track revealed hidden information (e.g., cards the opponent played from hand) for belief-state modeling.
- Keep every experiment reproducible and documented as you go: the Strategy report (70% methodology) is written from this repo's history.
- **Search agent (Slice 2).** `ptcg.agents.search_agent` implements ISMCTS on top of the engine's `search_begin`/`search_step`/`search_end` forward model — `search_begin` only works on the real agent's own `Observation` (it cannot be seeded from a fabricated/foreign one), and every search iteration re-begins its own determinized search (no tree reuse across `search_begin` calls). Hidden info is filled in by a **belief v1 mirror-prior determinization** — unknown zones (opponent hand, both players' prizes, face-down active) are sampled from a mirrored prior over the visible pool rather than tracked precisely. Tree children are keyed by **content signatures** (card ID / attack / target identity), never by option index or engine serial, since those are not stable across determinizations. The opponent is modeled during rollouts/search as a **fixed heuristic-v0 policy** (not itself searched). A **v0-improvement gate** (`deviate_min_visits=20`, `deviate_value_edge=0.12`) means the search only overrides the heuristic-v0 move when a challenger move has been visited at least 20 times AND beats v0's move by at least 0.12 in value — otherwise it defers to v0. Search **falls back to heuristic-v0 on any failure** (search error, timeout, no completed iteration), so a broken search path degrades to v0 rather than crashing or timing out the match. **Status:** tuned search-v1 (evaluator-v2 KO-awareness + rollout_depth=12 + the v0-improvement gate above) measures **parity** with heuristic-v0 (~47–49% win rate over 600+ mirror games in `experiments/EXPERIMENTS.md`) — not a genuine edge; the hand-tuned evaluator is treated as a ceiling, documented in the `tests/test_search_acceptance.py` docstring. Slice-2 closed here deliberately: **the ladder submission (`src/ptcg/submission_main.py`) still uses `HeuristicAgent`, not the search agent** — search-v1 is repo-side infrastructure only. The `_cost_satisfied` RAINBOW-energy over-count bug in `ptcg/search/evaluate.py` was fixed in Slice 4 (commit `876ea60`).

- **Learned value net (Slice 4).** `ptcg/search/features.py` (40-feature extractor, shared verbatim by training and serving), `ptcg/search/value_net.py` (pure-stdlib inference, no torch/numpy at serve time, 0.80 ms/eval), `ptcg/search/value_net_weights.json` (trained weights + embedded golden vectors for a non-circular parity test), `scripts/generate_training_data.py` (v0-self-play data generator) and `scripts/train_value_net.py` (torch training + export, `torch` is a dev-only dependency) together replace the seed KO-term hook with a trained evaluator. **Result:** the net decisively beats the hand-tuned evaluator offline (val AUC 0.8971 vs 0.7640, BCE 0.3955 vs 0.6079, on 264k held-out positions from 13,500 games / 1.33M positions) but arena win rate against heuristic-v0 stayed at parity even with the stronger evaluator (replicated gate FAIL, pooled 299/600 = 0.498 vs the 0.55 bar) — **evaluator quality was not the search's binding bottleneck**; the Slice-5 suspect is the search architecture itself (v0-improvement gate thresholds, determinization noise, iteration budget). Per spec's fail path, the ladder submission (`src/ptcg/submission_main.py`) is unchanged and still uses `HeuristicAgent`; the value net is repo-side infrastructure only, injectable via `SearchAgent`/`run_arena --rollout-depth` for future experiments. See `experiments/EXPERIMENTS.md` and the memory `slice4-status-and-carryforwards.md` for the full run log.

- **Search architecture (Slice 5).** Diagnosed the Slice-4 parity result via four measurements (D1-D4) plus one intervention (F3); full evidence in `experiments/ANALYSIS-slice5-search-architecture.md`. Gate starvation ruled out: mean iterations at the 200ms operating budget (53.99) sit ~2.7x above the 20-visit `deviate_min_visits` floor, and raw search-vs-v0 disagreement is 33.5-36.0% across all four D1 budget tiers (200/500/1000/2000ms), with the v0-improvement gate vetoing 83-91% of it (compressing to the observed 3.2-5.7% deviation rate). Gate-as-bottleneck ruled out: a gate-off ablation (D3) produced win rates statistically indistinguishable from the gated series at both budgets tested (45.7% vs 45.0% at 200ms, 48.3% vs 42.0% at 1000ms, both gaps inside one CI width). Budget starvation ruled out: a 10x budget sweep produced no monotonic win-rate gain (45.0% -> 52.0% -> 42.0% -> 54.0%, all CIs overlapping 50%), and the match-clock envelope math shows ~48x timeout headroom at the 200ms operating budget (9,657ms provably-safe per-move ceiling against the observed max of 31 decisions/game and a 20.1ms worst-case overshoot, 2x hardware safety factor). Determinization noise ruled out: re-running search from 50 real-game states 20 times each at 200ms produced the same modal move 98.1% of the time with a root-value standard deviation of only 0.031. The one untested cheap lever, the final-move selection rule (F3, `max_value` vs. default most-visited), was then intervention-tested directly and also plateaued (0.510 [0.441, 0.578], CI spanning 0.50). **Result: documented dead-end.** No configuration across D1/D3/F3 produced a win-rate CI wholly above 0.50, so the Task-14 replicated acceptance gate was not run (no configuration cleared the noise floor worth spending it on). Per spec's fail path, the ladder submission (`src/ptcg/submission_main.py`) stays unchanged on `HeuristicAgent`. Leading hypothesis for the residual parity: the value net was trained exclusively on v0-self-play data, so search lines that deviate from v0's policy are scored off-distribution exactly where accuracy matters most, and rollouts/the opponent model score both sides as the same fixed heuristic-v0 policy, capping the lookahead advantage the search can surface. Armed as Slice-6 debt (F4): retrain the value net on mixed-policy (search-included) data and use it as a PUCT prior rather than a leaf evaluator; the equally-consistent alternative hypothesis (the symmetric mirror matchup may simply have little exploitable per-decision edge) is also carried forward, unresolved.

- **Mixed-policy value net + root PUCT prior (Slice 6).** Tested the Slice-5 F4 hypothesis (off-policy value blindness) directly before spending compute to fix it. Phase-0 diagnostic (D0): game-level deviation tagging plus an hte-differential control isolated net-specific degradation from shared search-game difficulty. CONFIRMED: post-deviation AUC deficit = 0.0806 (>= 0.05 bar) and differential (net minus hand-tuned evaluator, same rows) = 0.0452 (>= 0.03 bar) - roughly 44% of the raw deficit is shared-difficulty noise, the rest is net-specific off-policy blindness. Fix 1 (Stage 1): retrained on 172,829 search-policy positions (overnight generation, 1,350 games, blended at ~11.5% of the combined 1.5M-row training set) into `src/ptcg/search/value_net_weights_v2.json` (loadable via `--net-weights`); held-out post-deviation AUC recovered 0.8168 -> 0.8751 (72% of the deficit closed) with zero on-policy regression (0.8971 -> 0.8979). Stage-1 arena gate (2x300 games, replicated) FAILED at parity: pooled 301/600 = 0.5017 vs the 0.55 bar. Fix 2 (Stage 2): a value-derived root PUCT prior (`use_root_prior`/`prior_tau`/`c_puct`, flag-off by default, bit-identical when off) redirects exploration toward the net's top-ranked root actions instead of just re-scoring leaves. Stage-2 gate (2x300, replicated) also FAILED at parity: pooled 283/600 = 0.4717. **Both fixes worked at their own level (the evaluator got measurably better and was even handed control of exploration) and neither moved arena win rate** - the evaluator-quality family of hypotheses is now closed end to end across Slices 4-6. Two sharpened candidates carried forward for Slice 7+: (1) policy reach, not value accuracy - rollouts and the opponent model still play both sides as heuristic-v0, so a deviation is scored under the assumption neither player ever deviates from v0, which no leaf evaluator or root prior can fix; the shape of a fix is a policy-improvement loop (search-guided rollouts / iterated self-play), a full slice of its own; (2) the no-exploitable-edge alternative - every Slice 4-6 arena result (gated, gate-off, budget-swept, selection-rule-swept, retrained, prior-steered) sits in [0.42, 0.54] on the symmetric mega-lucario mirror, so an asymmetric-deck-pairing discriminating test is the cheap next check before committing another slice to the search itself.
