# Replicate a stochastic gate before recording it, when it's near its bar

Any acceptance/regression gate whose input is a finite random sample (an N-game arena series, a win-rate threshold) is itself a random variable. A single run that clears the bar is not evidence the underlying win rate clears the bar — it may just be a favorable draw. Before committing a result as "the gate passed" or writing the number into EXPERIMENTS.md / a spec / a docstring, run it a second time (same config) whenever the result sits close to the threshold (within roughly one confidence-interval width, or when the decision hinges on the number).

**Datapoint (2026-07-09, Slice 2 T9):** the revised acceptance bar (>=0.48, LCB>0.40) was tested with a 200-game run that PASSED. A second 200-game run on the identical shipped config FAILED (91-109, 45.5%). Committing after the first run alone would have shipped a flaky gate and a false "search-v1 beats the revised bar" claim into the project record. The honest resolution (three total runs: pass, fail, pass; pooled ~47-49%) was only visible because a second run was demanded near the bar.

**Practical rule:** when a stochastic gate's result is close enough to its threshold that a plausible second sample could flip the verdict, run it again before recording anything. Report BOTH (or all) runs verbatim — do not report only the run that supports the claim you want to make. This is the stochastic-testing-specific instance of the "subagent self-reports/numeric claims are unreliable" family (global CLAUDE.md → Subagent Discipline): the unreliable narrator here is chance, not a subagent, but the fix is the same — demand a second independent observation before trusting the first.

## Refinement: a margin-based tripwire does not converge when the bar is re-derived from the same pool (2026-07-09, Slice 3 T12)

The margin-rule above works for a **fixed, externally-set** bar. It breaks down for a **regression-pin gate whose bar is itself derived from the same pool being tested**: re-deriving the bar from the pooled result after each near-miss just makes the bar chase the pool — a margin-based "run it again" tripwire never converges in that setup (observed: 3x200-game draws at 0.630/0.650/0.565 all technically passed a moving margin check; re-deriving the bar from the pooled 600 games produced a second tripwire fire on the very next run).

**Resolution used:** stop re-deriving the bar after every fire. Instead, fix the bar ONCE from a sufficiently large pooled sample and evaluate future near-bar results on the **false-trip PROBABILITY** implied by that fixed pooled estimate (not on a moving margin). Slice-3 T12 closure: bar fixed at 0.49 from an 800-game pool (476/800 = 0.595 pooled win rate), with 4/4 recorded runs passing and an estimated false-trip probability of <=~2% worst case — no further replication demanded once that bar was set.

**Practical rule:** reserve the plain margin-based "run it again" tripwire (above) for single-run/fixed-bar gates. For a **regression-pin gate whose own bar is derived from the pool under test**, fix the bar once from a sufficiently large pool, then gate further near-bar results on the false-trip probability computed from that fixed pooled estimate — never re-derive the bar after every near-miss, or the tripwire chases its own tail indefinitely.

## Refinement: replicated gates keep catching noisy single-run probes — treat every probe number as provisional (2026-07-10/11, Slice 6)

A single-run probe-stage number in this repo has now been wrong in the optimistic direction three separate times in one slice: probe-stage win rates of 54%, 52%, and 52% (across different Slice-6 experiments — a mixed-policy-retrain probe, a PUCT-prior probe, and one more) all looked promising enough to justify running the full replicated gate, and all three pooled to <=0.50 once actually run at the pre-registered 600-game scale. In every case the probe was directionally misleading, not just noisy in magnitude — each one implied "this configuration might clear the bar" and the replicated gate said no.

**Practical rule, extended:** on measurement-heavy slices (evaluator diagnostics, search-architecture tuning — not just feature-acceptance gates), treat a single-run probe number as a "worth running the full gate" signal ONLY, never as a preliminary result to report or reason about. Do not narrate a probe's win rate in an analysis doc as if it carries evidentiary weight on its own; write it as "probe suggested X, replicated gate confirmed/refuted." This is the same underlying phenomenon as the original datapoint above (chance is an unreliable narrator), re-confirmed at 3x frequency in a single slice — the replication discipline earns its cost even when — especially when — the probe looks good.

## Refinement: pre-registered-blind threshold amendments are legitimate under three conditions (2026-07-10/11, Slice 6)

A pre-registered decision criterion (a CONFIRMED/not-confirmed bar, a gate threshold) can legitimately be amended mid-slice without compromising the "pre-registered, not post-hoc-rationalized" property that makes pre-registration meaningful in the first place — but only if the amendment satisfies all of the following:

1. **Proposed and decided before the deciding data exists.** The amendment must be locked in before the run/generation that would be judged against it has produced results — not after seeing a borderline number and being tempted to move the goalposts.
2. **Strictly conservative direction.** The amendment can only make the bar harder to pass (demote a would-be CONFIRMED to a non-confirm), never easier (promote a would-be fail to a pass).
3. **Explicitly approved by the human owner**, not silently adopted by the agent.

**Datapoint (Slice 6 D0):** the diagnostic's original pre-registered bar was a raw-deficit-only threshold (deficit >= 0.05). Before Phase-0 data generation ran, the design was amended to add a second, stricter requirement — the net-vs-control differential must ALSO clear >= 0.03 (see `.claude/rules/diagnostic-control-evaluator.md`) — Brad-approved in the same pre-generation window. Because the differential check can only ever make CONFIRMED harder to reach (a high raw deficit with a low differential now fails where it would have passed under the original rule alone), this satisfies condition 2. Pass 2 independently verified condition 1 by comparing commit timestamps: the amendment commit (`a2ff147`) provably precedes the data-generation commit (`0dbd447`) in the repo history, so the amendment could not have been reverse-engineered from a look at the results.

**Practical rule:** when a slice proposes amending a pre-registered criterion mid-flight, verify all three conditions explicitly before accepting the amendment as legitimate — and at review time, verify condition 1 with an artifact (commit-timestamp ordering, a plan.md edit timestamp), not just a prose claim that "this was decided before we saw the data." A reviewer/Pass-2 dispatch auditing a pre-registered-and-amended gate should be told to check the commit graph, not just read the prose narrative.

## Re-confirmation: a pre-registered replication *trigger* that correctly abstains is as valuable as one that fires (2026-07-14, Slice 7A)

**Datapoint (Slice 7A T2, asymmetric-pairing test):** the single-run FLAT decision ("no search edge", diff -0.0078, CI spanning 0) was pre-registered with an explicit replication trigger — replicate only if the CI bound landed within 0.02 of the decision boundary. The observed CI sat comfortably clear of that band, so the trigger correctly did NOT fire and one run was sufficient. This is the mirror-image confirmation of the fire cases above: pre-committing the *condition under which a second run is owed* (rather than "always replicate" or "never replicate") is the settled pattern — it demands replication exactly when the number is close enough to the bar to be flaky, and licenses a single run when it isn't. Pre-register the trigger, not a fixed replication count.

## Refinement: a pre-registered bar must be checked against the metric's achievable CEILING under the implemented algorithm before it is locked in (2026-07-14, Slice 7B)

Everything above governs *replication discipline* (when to re-run, when an amendment is legitimate) — this is a distinct, earlier failure: the bar itself can be unreachable by construction, independent of noise or sample size, and no amount of replication reveals that. A pre-registered threshold on a derived/learned metric (argmax agreement, an AUC floor, a win-rate bar) implicitly assumes the metric CAN reach that value under the algorithm actually implementing it. If the underlying representation collapses distinct cases to the same signature (feature collisions, lossy encodings, tied/duplicate targets), there is a hard ceiling below which no amount of training, tuning, or replication will ever clear the bar — and a single run's FAIL looks identical to "genuinely not learnable yet" whether or not the ceiling is the real cause.

**Datapoint (Slice 7B gate 1, sanity):** the pre-registered floor was policy-net top-1 (argmax) agreement >= 0.60 against search's chosen move. The first real 14,154-decision run measured 0.2874 — a clean FAIL, but a diagnosis (opus, executable receipts against the real dataset, not a fixture) found the true ceiling was **0.5197**: 52.3% of decisions had the target option's action-feature vector exactly duplicated by a competitor in the same decision, so no scorer function of those features could ever discriminate the tie. The 0.60 floor was mathematically unreachable before a single weight was trained. Two subsequent featurizer generations (closing the identified collision mechanism each time) raised the ceiling only to 0.5446 and then 0.5448 — confirming the ceiling, not the floor, was the binding constraint throughout.

**Practical rule:** before locking in a pre-registered threshold on any derived/learned metric, compute (or tightly bound) the metric's achievable ceiling under the ACTUAL implemented representation — not an idealized version of it. For a classification/agreement-style metric, this usually means: how many groups of inputs share an identical feature signature (a collision/duplicate-rate check) and what score a perfect-information oracle could achieve given those collisions. If the ceiling is close to or below the proposed floor, the gate has no fail-power in either direction — a FAIL doesn't distinguish "not learned yet" from "unlearnable," and a PASS would have been a coincidence. This ceiling check is a plan-time (or spec-time) step, done once before any data generation — cheap relative to the generation + training runs a bar re-check requires after the fact. Where amending the bar downward is warranted by a ceiling finding, route the amendment through the three-condition legitimacy test above (proposed before the deciding run, strictly conservative, human-approved) — Slice 7B's two amendments (`d034ab6`, `7df62ee`) both did this correctly.
